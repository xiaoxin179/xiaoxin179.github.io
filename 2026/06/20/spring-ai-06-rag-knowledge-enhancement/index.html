Spring AI RAG 与知识增强

RAG 是什么——为什么光靠 Prompt 不够

上一模块讲过 RAG 的概念，这里在实战模块里再讲一遍，视角不一样——重点是为什么要用 RAG，以及怎么理解它在代码里的位置。

一、模型的知识边界

大模型有两个根本限制，必须先搞清楚：

限制一：训练截止日期

模型的知识来自训练数据，训练完成后知识就固定了。2024 年发生的事，如果不在训练数据里，模型就不知道。问它”上周的股价是多少”，它答不了。

限制二：不知道你的私有数据

模型从公开数据训练，公司内部文档、产品手册、历史订单，模型一概不知道。问它”我们产品的退货政策是什么”，它也答不了，或者会编一个。

所以：

  • 公司内部知识库问答 → 需要 RAG

  • 基于最新资讯的问答 → 需要 RAG

  • 基于用户个人数据的问答 → 需要 RAG

二、为什么不直接把资料塞进 Prompt

“我直接把整个文档塞进 System Prompt 不就好了？” 我听到这个问题很多次。

可以，但有几个问题：

  1. 上下文窗口有限：即使长上下文模型支持 100 万 Token，一个企业的知识库可能有几千份文档，几亿个 Token，塞不下。

  2. 成本极高：每次请求都带上所有文档，费用是正常请求的几百倍甚至更多。

  3. 效果不一定好：模型处理超长上下文时，注意力会分散，找中间的信息准确率比开头结尾低。

RAG 的方案是：不把所有文档都塞进去，而是先检索出和问题最相关的几段，只把这几段塞进去。

三、RAG 的完整流程

RAG 分两个阶段：

阶段一：文档入库（离线，一次性）

阶段二：问答检索（在线，每次问答）

四、为什么相似度检索能找到相关内容

这是 Embedding 的核心。在模块一讲过，Embedding 把文字转成向量，语义相似的文字，它们的向量在空间里距离近。

用户问”退货要几天？”，转成向量后和”退货政策”向量很接近，所以能找到退货政策相关的文档段落。

这就是为什么关键词搜索（ElasticSearch）找不到的内容，向量检索可能找到——关键词不匹配但语义相近的内容，向量检索能召回。

七、RAG 的局限性

知道 RAG 能解决什么，也要知道它的局限：

局限一：检索质量决定回答质量

如果向量检索没找到相关文档，或者找到的文档不够准确，模型就没有好材料回答。所以文档切片的质量、Embedding 模型的好坏，都直接影响最终效果。

局限二：切片方式影响检索效果

文档切片太短，每段语义不完整，模型看不懂；切片太长，一段里混了多个主题，检索不精准。怎么切是个技术活，下一节详细讲。

局限三：多跳推理能力有限

如果问题需要关联多段文档才能回答（比如”我符合优惠活动条件吗”，需要同时查用户信息和活动规则），基础 RAG 处理起来效果一般。这需要更复杂的 Agent 架构，后面会讲。

重叠（overlap）为什么重要

假设一段话刚好跨越了两个切片的边界，没有重叠时两边都不完整，检索出来模型读了也懵。设置 overlap=100 后，上一段的最后 100 个 Token 会出现在下一段的开头——这 100 个 Token 的信息冗余是值得的，能保证语义不断层。

检索增强问答

前两节干了不少脏活——文档加载、切片、向量化、入库，一堆配置和坑。但那些都是准备工作，真正有意思的在这节。

把检索端接上 ChatClient，整个 RAG 系统就活了。用户问一个问题，系统自动去向量库里找相关内容，塞给模型，模型基于这些内容回答——这才是那两节折腾的意义。

一、QuestionAnswerAdvisor：一个 Advisor 搞定 RAG

还记得之前讲的 Advisor 机制吗？Spring AI 提供了 QuestionAnswerAdvisor，它就是个 Advisor，在每次调用模型之前自动干四件事：

  1. 把用户的问题转成向量

  2. 在向量库里检索 Top-K 相关文档

  3. 把检索结果注入 Prompt 的上下文

  4. 带着这些上下文去调用模型

整个 RAG 流程一行代码挂上去就完事了，不需要手动写检索逻辑。

五、RAG 效果调优

RAG 上线后最常见的问题就是”回答不准”。我说实话，这个问题没有银弹，但有排查思路。

第一步：先查检索质量

用 /search 接口看检索结果。如果检索到的文档根本不相关，问题在检索端，不是模型的问题：

  • 调低 similarityThreshold（从 0.7 调到 0.5 试试）

  • 增加 topK（多检索几条候选文档）

  • 检查切片策略，太短或太长都会影响检索精度

第二步：检查文档质量

检索结果是对的，但模型回答还是偏——大概率是 System Prompt 约束不够，或者原始文档描述模糊。我见过最多的情况是文档本身写得很差，内容含糊，这时候优化 Prompt 也救不了。

第三步：问题改写（Query Rewriting）

用户的问题往往口语化，比如”我买的东西想退掉怎么搞”，直接拿去检索效果很差。可以先让模型改写成规范表述再检索：
