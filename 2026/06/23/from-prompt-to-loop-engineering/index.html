从 Prompt 到 Loop：Agent 工程正在从提问走向闭环

最近读到 Datawhale 的一篇文章《一文搞懂！Loop Engineering 的进化史和本质》，里面有个判断很值得记下来：Agent 的使用方式，正在从“人写提示词让模型干活”，转向“人设计一个循环系统，让系统持续驱动 Agent 干活”。

这不是简单换一个热门词。它背后其实是 AI 工程协作方式的一次升级：我们不再只关心怎么把一句话问得更好，而是开始关心一个任务如何被触发、执行、验证、修正，并在必要时停下来。

一、为什么 Prompt 不够了

早期使用大模型，核心动作就是写 Prompt。

你把背景、要求、示例、输出格式一次性塞进上下文里，然后期待模型给出稳定结果。这个阶段的问题也很明显：模型只能基于它“看到”的内容工作。没给它的背景，它只能猜；没写清楚的约束，它大概率会忽略。

后来大家开始讲 Context Engineering。重点从“怎么问”变成“让模型看到什么”。系统提示词、few-shot 示例、RAG 检索、结构化输入，本质上都是在改善模型的输入环境。

但上下文再完整，也解决不了所有问题。

比如让 Agent 修一个 CI 失败：它要读日志、定位代码、修改实现、跑测试、根据错误继续调整，最后提交结果。这不是一次回复能完成的任务。它需要工具、执行环境、反馈机制和多轮决策。

于是就有了 Harness Engineering。像 Claude Code、Cursor、Codex 这类工具，本质上都是给模型装上“手脚”：能读写文件、跑命令、调用外部服务、观察结果，并在一个 session 里推进复杂任务。

但 Harness 解决的是“Agent 能不能做事”。它还没有解决另一个问题：为什么每次都要人来按开始键？

二、Loop 解决的是人的重复介入

如果一个 Agent 已经能修代码、跑测试、开 PR，但每天仍然需要你手动检查 CI、复制错误日志、发给 Agent、等它修、再做 review，那么瓶颈就不完全在 Agent 身上，而在这个流程还依赖人类手动驱动。

传统定时任务的逻辑通常是写死的：如果 A，就执行 B；如果失败，就退出。Loop 里面的关键决策者是 LLM。它不是机械地执行固定脚本，而是根据观察到的状态判断下一步该怎么做。

比如同样是 CI 红了，系统可能判断这是一个 flaky test，也可能判断是依赖版本变化，还可能发现需要拆成多个改动分步处理。这里的价值不在“定时”，而在“能根据反馈继续调整”。

三、一个可运行 Loop 通常需要什么

把 Loop 拆开看，它大概需要六类能力。

1. Automations：触发机制

Loop 需要被唤醒。触发方式可以是定时任务、webhook、CI 失败事件，也可以是某种周期性的状态检查。

没有触发器，系统再聪明也只是待机。

2. Worktrees：隔离工作区

多个 Agent 任务并行时，不能都挤在同一个目录里改代码。独立的 git worktree 可以让每个任务拥有自己的工作区，互不覆盖，也方便回收失败尝试。

3. Skills：项目规则

Agent 每次启动都从零理解项目，会浪费大量上下文，也容易反复踩同样的坑。

把编码规范、架构约定、常见命令、测试方式沉淀成类似 AGENTS.md、CLAUDE.md、SKILL.md 的规则文件，本质上是在给 Agent 提供稳定的项目记忆。

4. Connectors：连接外部系统

真实工程任务不只发生在代码目录里。Agent 可能要读 GitHub issue、开 PR、更新 Linear、发 Slack 通知、查数据库。

这些能力通常需要通过 MCP、API 或命令行工具接入。

5. Sub-agents：独立检查者

写代码的 Agent 不适合完全负责验证自己的结果。它犯错的盲区，往往也是它自查时看不见的地方。

所以更可靠的做法是让另一个 Agent、另一套规则，甚至另一个模型来做 review 或验证。这里的重点不是“多一个模型更热闹”，而是让检查信号尽量独立。

6. Memory/State：跨轮状态

Loop 会一次次醒来，但模型上下文不会天然记得上次发生了什么。

因此系统需要把尝试过的方案、失败原因、当前进度、退出条件写到磁盘或数据库里。这样下一轮才不是重新开始，而是在已有状态上继续推进。

在 Agent 场景里，LLM 和编排逻辑像控制器，负责判断下一步；工具调用层像执行器，负责把决策变成动作；测试、lint、review、监控指标则像传感器，负责告诉系统离目标还差多远。

这个视角很重要，因为它提醒我们：Loop 的关键不只是让 Agent 多跑几轮，而是让每一轮都能拿到足够好的反馈信号。

如果传感器只返回一句“失败了”，Agent 的下一步几乎是在猜。

如果传感器能返回哪个测试失败、哪个断言不满足、哪个文件引入了差异、哪个接口行为被破坏，Agent 的修正空间就会立刻缩小。

所以，很多时候真正高杠杆的地方不是买更强的模型，而是设计更好的验证系统。

一个普通 Prompt 配上强验证，往往比一个精致 Prompt 配上弱验证更容易收敛。

五、什么时候不该急着做 Loop

Loop 很诱人，但不是所有任务都适合闭环化。

我觉得可以先问一个问题：

你能不能写出一个自动检查，稳定拒绝坏结果？

如果答案是不能，那这个任务大概率还不适合交给 Loop。

比如“让代码更优雅”“写一篇好文章”“设计一个更合理的 API”，这些目标当然重要，但它们很难直接变成客观的 pass/fail。你可以让另一个 LLM 打分，但 LLM 的审美和判断也会漂移，它给出的“通过”并不一定可靠。

更适合 Loop 的任务通常有几个特征：

  1. 重复出现，比如每周都会发生。
  2. 有明确的客观验证，比如测试、构建、静态检查、监控指标。
  3. Agent 有足够工具观察现场，而不是只能凭空猜。
  4. 失败成本可控，系统能在超过预算或连续失败后停下来。

换句话说，先不要急着自动化“判断力本身”。更好的起步方式是：先沉淀项目规则，再设计验证器，最后才加自动触发。

先建 Inspector，再建 Loop。

六、对个人开发者的启发

对我这种写后端、折腾 Agent 工具的人来说，Loop Engineering 最有启发的地方是：Agent 工程的中心正在从“写一次好提示词”转向“设计一个可收敛的工作系统”。

以后评价一个 Agent 工作流，可能不能只看它用了什么模型、Prompt 写得多漂亮，而要看这几个问题：

  1. 它什么时候启动？
  2. 它能操作哪些真实工具？
  3. 它怎么知道自己做对了？
  4. 它失败后如何缩小问题范围？
  5. 它什么时候停止并把问题交还给人？

这些问题回答清楚了，Agent 才不只是一个聊天窗口，而是一个工程系统里的执行单元。

Loop 放大的不是模型本身，而是系统设计者的判断力。你能把目标、约束、验证、状态设计得多清楚，Agent 就能在多大程度上替你持续推进。

小结

Prompt Engineering 关心怎么问。

Context Engineering 关心让模型看到什么。

Harness Engineering 关心 Agent 能不能使用工具完成多步任务。

Loop Engineering 关心的是：这些能力能不能被组织成一个会自我修正的闭环。

真正值得投入的，不一定是继续打磨一句万能 Prompt，而是把重复任务拆成可触发、可执行、可验证、可恢复的系统。尤其是验证这一环，它决定了 Loop 是稳定收敛，还是带着自信跑偏。
