grill-me skill：先把需求问明白，再让 AI 动手

Vibe Coding 最容易出问题的地方，不是“AI 不会写”，而是“你自己还没想清楚就开始写”。

很多返工，其实不是代码返工，而是需求返工。今天想要一个功能，明天发现边界没定义，后天又补了一堆例外条件，最后整个项目被推倒重来。

grill-me skill 的思路很直接：别急着写，先把你审明白。

一、为什么它会火

这类 skill 能火，不是因为它多复杂，恰恰相反，是因为它很简单。

它不教 AI 怎么实现功能，而是改 AI 的协作姿态。

平时是你下命令，它执行。
用了 grill-me 之后，变成它先追问你，把那些你没想好的地方一层层逼出来，再开始动手。

这件事对“高返工成本”的任务特别有用。因为真正贵的，往往不是写代码本身，而是方向错了以后再回头改。

二、它到底做了什么

grill-me 的核心就三件事：

  1. 把方案的每个分支都问清楚，直到双方对同一件事有共同理解。
  2. 一次只问一个问题，问完再问下一个。
  3. 能从代码库里自己查明白的，就别来问人。

听起来像废话，实际上很锋利。

它不是“帮你更快开工”，而是“帮你别在错误的方向上开工”。

它的核心指令其实非常短：

翻译成人话就是：把方案的每个细节问到双方理解一致；沿着设计树逐层推进；一次只问一个问题；能查代码得到的答案就先自己查。

三、为什么“一次只问一个”这么关键

这条其实最值钱。

如果 AI 一口气抛给你五六个问题，大多数人都会懵：哪些是主问题，哪些是次问题，哪些是可以先不管的？

一次只问一个，就能强迫讨论沿着决策树往下走。

先定最上游的决定，再定下游的细节。比如：

  • 先定这个东西到底面向谁
  • 再定它解决什么问题
  • 再定数据从哪来
  • 再定结果怎么输出

顺序一乱，后面问得再认真也容易白问。

四、它为什么比“直接开干”更稳

它本质上是在提前做风险控制。

很多返工，都是因为你当时没有意识到某个岔路口存在。比如：

  • 要不要记住历史结果
  • 重复内容怎么去重
  • 失败了是重试还是跳过
  • 输出给谁看，推送到哪里

这些问题如果等代码跑起来才发现，修起来就会牵一发动全身。

grill-me 的价值，就是把这些后置问题前置。

五、一个实际例子：自动抓取热点并推送

文章里的例子很典型：只给 AI 一句话——“我想做一个每天自动整理 AI 热点、生成选题清单并推送给我的助手”。

如果直接进入 Vibe Coding，AI 很可能马上开始写爬虫、建项目、装依赖。使用 grill-me 后，它先检查已有的 skill 和 MCP 工具，发现搜索、飞书推送、定时任务等能力已经存在，于是优先考虑把现有能力编排起来，而不是重复造轮子。

接下来它会逐个确认：热点属于哪些领域、应该抓哪些来源、每天生成几条、何时推送、推送到哪里，以及如何避免同一个热点连续多天重复出现。

这些问题看起来琐碎，却决定了最终做出来的东西是不是“真正想要的东西”。

六、如何让任意 AI 使用这种方式

如果你希望把它注册成可以反复调用的全局 skill，就不必依赖某个仓库或安装命令，可以直接让具备本地文件操作能力的 AI 帮你创建并安装。

七、它和 Plan Mode 的区别

Claude Code 里的 Plan Mode，偏向快速产出计划，目标是尽快进入执行。

grill-me 则相反，它不急着给结论，先把脑子里的糊涂账捋清楚。

简单说：

  • Plan Mode 更像“先给你一份计划”
  • grill-me 更像“先把需求审到没歧义”

两者不是对立的，更像前后配合。

我更喜欢的顺序是：

  1. 先用 grill-me 把方案问清楚
  2. 再进 Plan Mode 出计划
  3. 最后正式动手

八、它适合什么，不适合什么

适合：

  • 要做几小时甚至几天的功能
  • 一旦方向错了，返工成本很高的任务
  • 产品点子、选题方向、课程大纲这类决策树很深的事情

不适合：

  • 改一个明显的小 bug
  • 调一个样式
  • 补一个一眼能看穿的小功能

这种场景再拿它来审，就会变成纯折磨。

九、一个更重要的结论

grill-me 真正厉害的地方，不是“会问问题”。

而是它把 AI 从一个猜你心思的执行工具，变成了一个逼你把心思说清楚的搭档。

它问你的每一个问题，其实都是你本来就该问自己的问题。

只是以前你常常跳过了。

结语

如果说 Vibe Coding 解决的是“快速开始”，那 grill-me skill 解决的就是“别把开始做成返工的起点”。

对于那些值得认真做的事，先问清楚，往往比先写出来更省时间。
