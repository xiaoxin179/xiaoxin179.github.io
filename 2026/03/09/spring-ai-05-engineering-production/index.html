错误处理、重试与降级策略

调用外部模型 API，不可避免会遇到各种错误。网络抖动、API 限流、服务器过载……这些都是正常现象。代码要能优雅地处理这些情况，而不是直接把异常抛给用户。

我这节从最基础的异常捕获讲起，一路到重试、熔断降级，把这套防御体系搭完整。

一、常见错误类型

先把常见错误归个类，知道是什么错才能针对处理：

| HTTP 状态码 | 错误类型 | 处理方式 |

| — | — | — |

| 401 | API Key 无效或过期 | 报警，不重试 |

| 403 | 无权限（比如未开通某个模型） | 报警，不重试 |

| 429 | 限流（请求太频繁） | 等待后重试，或切备用模型 |

| 500/502/503 | 服务端错误 | 重试 1-3 次 |

| 超时 | 网络或模型响应太慢 | 重试，或降级 |

| 余额不足 | API 账户额度用完 | 报警，切备用 |

Spring AI 会把这些 HTTP 错误包装成 HttpClientErrorException 或 HttpServerErrorException 的子类，结构很清晰，分支处理起来不麻烦。

生产注意事项、成本控制与常见踩坑

这节不讲新功能，讲的是我踩过的坑和见过的坑。把 AI 功能上生产，有一些问题必须提前想清楚，否则上线后才发现，修起来很麻烦。

一、Token 计算和成本控制


AI API 按 Token 收费，生产环境不控制成本，账单会让人崩溃。

什么是 Token，大概多少字

中文 1 个字 ≈ 1.5-2 个 Token，英文 1 个单词 ≈ 1-2 个 Token。

粗略估算：

  • 一次简单问答（问 50 字，答 200 字）：约 400-600 Token

  • 一次带对话历史的问答（10 条历史 + 本次）：可能超过 2000 Token

  • RAG 问答（检索出 3 段文档）：可能超过 3000 Token

控制 System Prompt 长度

System Prompt 每次请求都要带上，它的 Token 数直接乘以请求次数。1000 Token 的 System Prompt，每天 10 万次请求，光 System Prompt 就消耗 1 亿 Token。

所以 System Prompt 要写得精练，去掉废话，只保留真正有用的约束。

对话历史截断

多轮对话保留的消息越多，每次请求 Token 越多。不要无限保留历史，之前讲的 MessageChatMemoryAdvisor 保留最近 N 条就是出于这个考虑。

六、常见踩坑清单

快速过一遍我见过最多的坑：

| 坑 | 原因 | 解决方案 |

| — | — | — |

| 结构化输出偶发失败 | 模型有时不严格遵守 JSON 格式 | try-catch + 重试，或在 Prompt 里强调格式 |

| 对话历史越来越长，Token 超限 | ChatMemory 没有设消息数上限 | 设 lastN 参数，不超过 20 条 |

| API Key 泄露被盗刷 | 硬编码或提交到 Git | 环境变量 + .gitignore |

| 请求线程被长时间占用 | 同步等待 AI 响应 | 流式输出或异步处理 |

| 模型返回了 Markdown，前端显示乱 | System Prompt 没说明格式 | 在 System Prompt 里明确说”不要用 Markdown” |

| 高并发时触发 429 | 没有主动限流 | 应用层加 RateLimiter |

| 敏感信息随 Prompt 发给模型 | 没有脱敏处理 | 在 Advisor 里做输入脱敏 |

| 模型幻觉导致错误数据 | 没有数据校验 | 对 AI 输出做业务逻辑校验 |
